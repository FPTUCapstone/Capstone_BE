# TM-228 Staff and Administrator boundaries

Authority: [Report 3 on Drive](https://docs.google.com/document/d/1VwPkqRyC6ZlbXBQC0ztdektt0vAyE3qt/edit), non-V2 revision dated 2026-11-26. Relevant sections are 2.2.2, 3.6.7, 3.9.1 and 5.1. In UC-46 through UC-48, BR-168 includes Service Provider in the Staff scope.

Add `/api/v1/admin/users` list and `/{userId}` detail, and POST `/{userId}/lock` and `/unlock` with required reason. Backend limits Staff to Traveler, TourOperator and ServiceProvider targets; Administrator to Staff. Check the acting account's current DB role and Active status before data access. Apply scope before filters/count/page. Missing and out-of-scope targets have the same 404. DTOs allow-list public administration fields, never credentials. Reject unknown mutation properties (including role). Use existing immutable audit infrastructure for success and failure, and queue account notification in the same transaction.

Lock and unlock use serializable transactions and existing EF status concurrency token. Preserve status before lock, require reason and revoke every refresh token at lock. A persisted session version increments on lock; signed JWTs carry it and are rejected when stale even after unlock. This requires an idempotent database-first migration and explicit UTC mapping. No role editing or Traveler/Operator creation function is added.

Use existing debt and commission records for BR-189 and BR-200. Unlock returns HTTP 409 with `messageCode` set to `MSG199` and numeric `outstandingAmountVnd` for authorized Staff while settlement is pending. An automatic lock requires full settlement. A separate manual lock can be resolved during the applicable grace period. An outstanding debt or statement that has already reached the automatic-lock threshold still blocks reinstatement. When historic lock evidence is incomplete, keep the account locked.

Both the account and payout unlock endpoints require a reason and use the same settlement checks and lock evidence. The payout endpoint retains its Tour Operator response fields and targets only Tour Operators. Validate the reason, role and previous state before changing the account. Queue account notices and write audit in the same transaction. The Service Provider auto-lock job revokes refresh tokens and queues MSG210 for the provider and active Staff when it locks the account.

In UC-83, Staff records bank receipts for positive overdue or payment-reported statements. Staff verifies the bank reference and the amount credited to TripMate against the full commission due for that statement. Keep the provider-reported reference and timestamp, and record the verified reference separately so Staff can resolve an incorrect report. Audit both references and the matched amount. The project owner confirmed on 2026-11-28 that one bank transfer settles one statement. Apply `20261128_tm228_verified_commission_receipt.sql` before deploying the API. Historical paid references still reserve their matching bank references.

Confirming the last positive overdue receipt makes the account eligible for Staff unlock. Zero-commission statements remain visible and require no payment. Transitioning a positive unpaid statement to Overdue queues one MSG207 reminder for the statement. The BR-200 lock and MSG210 remain tied to the 15-day threshold. Sort reconciliation results by period, due date and statement ID for stable paging.

Staff handles operator applications, tour moderation, POI creation, Route operations, booking and active-trip monitoring, and landing content. Administrator handles algorithm settings, POI deactivation, reports, audit and failed payout details and actions. Both roles may update POIs and view the payout list. Match Web navigation and direct-route access to API authorization. Validate the Update POI (UC-52), Update Route (TM-102) and Landing CMS (TM-112) permissions when those endpoints are integrated.
