Client key scoped to creator; same normalized payload replays, changed payload returns 409.

## Approved independent group leave (2026-11-28; code only)
POST /api/v1/chat-groups/{id}/leave, Idempotency-Key: nonempty GUID, body {replacementHostUserId:long|null}. Returns 200 {groupId,membershipStatus:"Left",newHostUserId:long,leftAtUtc:UTC}. Active actor required. Nonhost omits replacement; supplied replacement returns400. Host must explicitly select an existing other Active-account member. Missing/invalid/ineligible replacement returns409; no eligible member returns409 with add/select replacement guidance. Never auto-select, delete or disband.
Durable leave receipt is scoped to group+actor+key, survives membership deletion, replays the original receipt before membership authorization, and rejects changed payload409. Group locking and serializable Result rollback protect transfer/removal/receipt and current read/send authorization; bounded contention retries. Postcommit user-bound ConversationChanged and MembershipChanged invalidations include departing actor and surviving Active recipients, contain only groupId. Independent IDs never authorize travel groups.
CreatedByUserId is immutable, backfilled from host before transfers. Creation uniqueness uses creator+client key; immutable normalized original member IDs preserve payload comparisons after departures. A departed creator's create replay returns409 rather than message-bearing data or creating a duplicate. Public conversation DTO remains unchanged.
GET /{id}/members adds canReceiveHost:boolean, true only for Active accounts other than current host; no account-status field. Leave independently revalidates target. FE delivery goes through parent only; no FE/Mobile edits.
Explicit idempotent SQL plus canonical schema and UTC EF mappings; no SQL execution. No tests/build/lint/analyze/browser per user. Source review and downstream handoff only; prior validation results do not cover leave.


## Approved independent ChatGroup host management (2026-11-28; code only)

DELETE /api/v1/chat-groups/{id}/members/{userId} -> 204, including an already absent target after current host authorization. No self/host removal. POST /api/v1/chat-groups/{id}/dissolve -> 204, including an already closed group after current host authorization. All three require an Active account, current membership and host identity; member nonhosts403, inaccessible404, invalid400, closed mutation409.
Conversation and member-list DTOs append isClosed:boolean (constructor default false). Dissolve retains memberships, messages and snapshot history. Active current members can list/read/mark-read, but closed groups reject send, rename, kick, new leave and transfer; prior durable leave receipts still replay without a new mutation. canReceiveHost is false when closed. No travel-group, booking or itinerary lifecycle effects.

Send checks closure before message replay; snapshot-share send authorization checks closure and nested SendChatGroupMessage enforces it inside the outer transaction. Snapshot history remains readable for current members. Postcommit rename/dissolve invalidate current Active recipients; kick uses the existing membership notifier including the departing user only when a member was actually removed.
